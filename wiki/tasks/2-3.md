# 2.3 — Distribute tools appropriately across agents and configure tool choice

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [2 — Tool Design & MCP Integration](../domains/2-tool-design-and-mcp-integration.md) (18%)

## What it tests

Two related things: how much tool surface an agent should have, and how to *force* tool behaviour when you need a guarantee.

## Knowledge

**Too many tools degrades selection reliability.** The guide's figures: 18 tools instead of 4–5 measurably increases decision complexity and reduces reliability. Breadth is not capability.

**Agents misuse tools outside their specialisation.** A synthesis agent given web search will attempt web searches — badly, and bypassing the agent you built for the job.

**Scoped access:** give each agent the tools its role needs, plus *limited* cross-role tools for specific high-frequency needs.

**`tool_choice` configuration:**

| Value | Effect |
|---|---|
| `"auto"` | Model decides whether to call a tool — may reply in prose instead |
| `"any"` | Model **must** call a tool, but chooses which |
| `{"type": "tool", "name": "..."}` | Model must call **this specific** tool |

## Skills

- Restrict each subagent's tool set to its role, preventing cross-specialisation misuse.
- **Replace generic tools with constrained alternatives** — e.g. `fetch_url` becomes `load_document`, which validates that the URL is a document.
- **Provide scoped cross-role tools for high-frequency needs** — e.g. a narrow `verify_fact` tool for the synthesis agent — while routing complex cases through the coordinator.
- Use forced `tool_choice` to guarantee a specific tool runs first (e.g. `extract_metadata` before enrichment), then handle subsequent steps in follow-up turns.
- Set `tool_choice: "any"` to guarantee a tool call rather than conversational text.

## Anti-patterns

- **Giving an agent the full toolset "so it can handle anything".** Over-provisioning; breaks separation of concerns.
- **Pure delegation for a high-frequency simple need.** If 85% of verifications are simple fact-checks, round-tripping all of them through the coordinator adds latency for no benefit.
- **Batching verification needs to the end.** Creates blocking dependencies, because later synthesis steps may depend on earlier verified facts.
- **Speculative caching** — pre-fetching extra context "in case the synthesis agent needs it" cannot reliably predict what it will need.

## Exam angle

The signature item: *"The synthesis agent frequently needs to verify claims. Currently it returns control to the coordinator, which invokes the web search agent, then re-invokes synthesis. This adds 2–3 round trips and 40% latency. 85% of these verifications are simple fact-checks; 15% need deeper investigation."*

The answer is the **scoped middle**: give synthesis a narrow `verify_fact` tool for the 85%, keep coordinator delegation for the 15%. Least privilege applied to the common case, without over-provisioning.

Distractor families: `over-engineered` (full web-search access — over-provisions and violates separation of concerns), `solves-different-problem` (batching — creates blocking dependencies), `unreliable-proxy` (speculative caching).

See [least-privilege tooling](../heuristics/least-privilege-tooling.md), which is largely built from this objective.
