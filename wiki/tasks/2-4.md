# 2.4 — Integrate MCP servers into Claude Code and agent workflows

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [2 — Tool Design & MCP Integration](../domains/2-tool-design-and-mcp-integration.md) (18%)

## What it tests

Where MCP configuration lives, how secrets stay out of it, and the tools-versus-resources distinction.

## Knowledge

**Scoping:**

| Scope | File | For |
|---|---|---|
| **Project** | `.mcp.json` | Shared team tooling, committed to version control |
| **User** | `~/.claude.json` | Personal and experimental servers |

**Environment variable expansion** in `.mcp.json` — `${GITHUB_TOKEN}` — lets you commit the configuration without committing the credential. This is the whole reason project scope is viable.

**All configured servers are active at once.** Tools from every configured server are discovered at connection time and available to the agent simultaneously. Project and personal servers coexist.

**Resources are not tools.** MCP **resources** expose content catalogues — issue summaries, documentation hierarchies, database schemas — giving the agent visibility into what exists **without spending exploratory tool calls to find out**. Tools are for actions; resources are for knowing what is there.

## Skills

- Configure shared MCP servers in project-scoped `.mcp.json` with environment variable expansion for authentication tokens.
- Configure personal and experimental servers in user-scoped `~/.claude.json`.
- **Enhance MCP tool descriptions** to explain capabilities and outputs in detail — otherwise the agent prefers built-in tools like `Grep` over a more capable MCP tool it does not understand.
- **Choose existing community MCP servers over custom implementations** for standard integrations such as Jira; reserve custom servers for team-specific workflows.
- Expose content catalogues as MCP resources to reduce exploratory tool calls.

## Anti-patterns

- **Inlining a token in `.mcp.json`** and committing it. Use `${ENV_VAR}`.
- **Putting a shared team server in `~/.claude.json`.** Nobody else gets it — the MCP mirror of [3.1](3-1.md)'s scoping failure.
- **Building a custom server for a standard integration.** Maintenance you did not need.
- **A thin MCP tool description.** The agent falls back to `Grep`. Same root cause as [2.1](2-1.md), different surface.
- **Forcing exploratory tool calls** where a resource would have shown the catalogue.

## Exam angle

Two clean shapes:

1. *"The team needs shared tooling; the token must not be committed"* → project `.mcp.json` + `${ENV_VAR}`.
2. *"Claude keeps using Grep instead of our MCP tool"* → the description does not explain what the tool can do.

Plus the resources item: *"The agent burns calls discovering what data exists"* → expose a catalogue as a resource.

Distractor families: `over-engineered` (custom server for Jira), `solves-different-problem` (adding more tools when the issue is description quality).

## In production, beyond the guide

Current docs define **three** scopes — local (the default, `~/.claude.json`, current project only), project (`.mcp.json`), and user (`~/.claude.json`, all projects) — with precedence local > project > user. `${VAR:-default}` fallback syntax is also supported. And note: `claude -p` runs and Agent SDK sessions load project-scoped servers **without** the interactive approval prompt. See the [drift log](../exam/drift-log.md#mcp-scopes--changed).

The guide's project-versus-user distinction is unaffected and remains the exam answer.
