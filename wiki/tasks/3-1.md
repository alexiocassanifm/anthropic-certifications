# 3.1 — Configure CLAUDE.md files with appropriate hierarchy, scoping, and modular organization

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [3 — Claude Code Configuration & Workflows](../domains/3-claude-code-configuration-and-workflows.md) (20%)

## What it tests

Where instructions live, who receives them, and how to keep a growing instruction set from becoming one unreadable file.

## Knowledge

**The hierarchy:**

| Level | Location | Reaches |
|---|---|---|
| **User** | `~/.claude/CLAUDE.md` | Only you, across all your projects |
| **Project** | `.claude/CLAUDE.md` or root `CLAUDE.md` | Everyone who clones, via version control |
| **Directory** | subdirectory `CLAUDE.md` | That directory's scope |

**User-level settings are not shared.** Instructions in `~/.claude/CLAUDE.md` do not reach teammates through version control. This single fact answers a whole family of exam items.

**`@import` keeps CLAUDE.md modular** — reference external files rather than inlining everything, e.g. importing the specific standards files relevant to each package.

**`.claude/rules/`** organises topic-specific rule files as an alternative to one monolithic CLAUDE.md.

**`/memory`** verifies which memory files are loaded and diagnoses inconsistent behaviour across sessions.

## Skills

- **Diagnose configuration hierarchy issues** — the classic case being a new team member not receiving instructions because they live in user-level rather than project-level configuration.
- Use `@import` to selectively include relevant standards files in each package's CLAUDE.md, based on maintainer domain knowledge.
- Split large CLAUDE.md files into focused topic files in `.claude/rules/` — `testing.md`, `api-conventions.md`, `deployment.md`.
- Use `/memory` to verify what actually loaded when behaviour differs across sessions.

## Anti-patterns

- **Team conventions in `~/.claude/CLAUDE.md`.** They work for you and nobody else. The single most testable failure in Domain 3.
- **One monolithic CLAUDE.md** that has grown past the point where any section gets attention.
- **Inlining every standard** instead of importing the relevant ones per package.
- **Guessing why behaviour is inconsistent** instead of checking what loaded.

## Exam angle

The signature item: *"A new team member isn't receiving the team's conventions."* → they are in user-level configuration; move them to project level.

Also expect the modular-organisation choice: when instructions have grown large, split into `.claude/rules/` topic files or use `@import`. And note the boundary with [3.3](3-3.md): if the conventions must apply to files **by type across many directories**, that is a `paths:` glob question, not a CLAUDE.md question.

Distractor families: `solves-different-problem` (fixing the instruction's wording when the problem is its location), `shifts-burden` (asking each developer to copy the file locally).

## In production, beyond the guide

Two additions and one genuine change:

- **Two more tiers exist**: managed policy (organisation-wide, e.g. `/Library/Application Support/ClaudeCode/CLAUDE.md` on macOS) and `CLAUDE.local.md` (personal, project-specific, gitignored).
- **`@import` has a maximum depth of four hops**; relative paths resolve against the importing file, not the working directory.
- **`/memory` versus `/context`** ⚠️ — current docs assign the "which files actually loaded" job to **`/context`**, while `/memory` lists locations and opens them for editing. **The guide says `/memory`, and that is the exam answer.** Use `/context` at your desk. See the [drift log](../exam/drift-log.md#memory-versus-context--changed-).

Also new: **auto memory**, a second system where Claude writes its own notes to `~/.claude/projects/<project>/memory/`. Not exam material.
