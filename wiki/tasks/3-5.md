# 3.5 — Apply iterative refinement techniques for progressive improvement

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [3 — Claude Code Configuration & Workflows](../domains/3-claude-code-configuration-and-workflows.md) (20%)

## What it tests

Four named techniques for converging on a correct result, and when each applies.

## Knowledge

**Concrete input/output examples are the most effective way to communicate expected transformations** when prose descriptions get interpreted inconsistently. Two or three examples beat another paragraph of explanation.

**Test-driven iteration:** write the test suite first, then iterate by sharing test failures to guide progressive improvement. The failures are precise feedback in a form the model can act on.

**The interview pattern:** have Claude ask *you* questions to surface considerations you had not anticipated, before implementing. Especially useful in unfamiliar domains.

**Batched versus sequential fixes:**

| Problems are… | Approach |
|---|---|
| **Interacting** — fixing one affects another | All issues in a single detailed message |
| **Independent** | Fix them sequentially |

## Skills

- Provide 2–3 concrete input/output examples to clarify transformation requirements when natural language produces inconsistent results.
- Write test suites covering expected behaviour, edge cases, and performance requirements *before* implementation, then iterate by sharing failures.
- Use the interview pattern to surface design considerations — cache invalidation strategies, failure modes — before implementing in unfamiliar domains.
- Provide specific test cases with example input and expected output to fix edge case handling (e.g. null values in migration scripts).
- Address multiple interacting issues in one detailed message; iterate sequentially for independent ones.

## Anti-patterns

- **More prose when examples would work.** The guide's point is that prose is where the inconsistency comes from.
- **Fixing interacting problems one at a time.** Each fix perturbs the others and you oscillate.
- **Batching independent problems** into one message unnecessarily — harder to attribute what changed.
- **Implementing in an unfamiliar domain without surfacing the unknowns first.** The interview pattern exists for exactly this.

## Exam angle

Match the symptom to the technique:

| Symptom | Technique |
|---|---|
| "A prose description of the transformation gets interpreted differently each time" | 2–3 concrete input/output examples |
| "Edge cases keep breaking after each fix" | Test-driven iteration; specific test cases with expected output |
| "Unfamiliar domain, unknown design considerations" | Interview pattern |
| "Several fixes that affect each other" | One detailed message with all of them |
| "Several unrelated bugs" | Sequential |

Distractor families: `over-engineered` (building tooling when examples would do), `solves-different-problem`.

Note the overlap with [4.2](4-2.md): both objectives say examples beat instructions. Here it is about a *developer* communicating a transformation; there it is about *prompt design* for consistency. The underlying fact is the same and worth carrying between them.
