# 4.3 — Enforce structured output using tool use and JSON schemas

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [4 — Prompt Engineering & Structured Output](../domains/4-prompt-engineering-and-structured-output.md) (20%)

## What it tests

The mechanism for guaranteed structure — and, more importantly, **exactly where that guarantee stops**.

## Knowledge

**Tool use with JSON schemas is the most reliable approach for guaranteed schema-compliant structured output**, eliminating JSON syntax errors. Define the extraction schema as a tool's input schema; read the result from the `tool_use` response.

**`tool_choice`:**

| Value | Guarantee |
|---|---|
| `"auto"` | None — the model may return text instead of calling a tool |
| `"any"` | Must call a tool, model chooses which |
| `{"type": "tool", "name": "..."}` | Must call this specific tool |

**The guarantee boundary — the most testable fact here:** strict schemas eliminate **syntax** errors but do **not** prevent **semantic** errors. Line items that do not sum to the stated total, values in the wrong field — all pass validation.

**Schema design:**
- Required versus optional fields
- Enum fields with `"other"` plus a detail string, for extensible categories
- Nullable fields where the source may not contain the information

## Skills

- Define extraction tools with JSON schemas as input parameters; extract data from the `tool_use` response.
- Set `tool_choice: "any"` to guarantee structured output when multiple extraction schemas exist and the document type is unknown.
- Force a specific tool with `{"type": "tool", "name": "extract_metadata"}` to ensure a particular extraction runs before enrichment steps.
- **Design schema fields as optional (nullable) when source documents may not contain the information** — this prevents the model from fabricating values to satisfy required fields.
- Add enum values like `"unclear"` for ambiguous cases and `"other"` plus a detail field for extensible categorisation.
- Include format normalisation rules in prompts alongside strict output schemas, to handle inconsistent source formatting.

## Anti-patterns

- **Required fields for information that may be absent.** A required field is an instruction to produce *something*. The model complies. This is the single cheapest hallucination fix in the domain.
- **Assuming the schema validates meaning.** It validates shape.
- **`tool_choice: "auto"` when you need guaranteed structure.** The model may reply in prose.
- **Prompting for JSON and parsing the text.** Tool use exists precisely to remove that failure mode.

## Exam angle

Two reliable shapes:

1. *"Extractions succeed but contain values not present in the source"* → nullable/optional fields.
2. *"Line items don't sum to the total, yet validation passed"* → schemas eliminate syntax errors, not semantic ones; semantic validation is [4.4](4-4.md)'s job.

And the `tool_choice` selection items: *unknown document type, several schemas* → `"any"`; *this extraction must run first* → forced selection.

Distractor families: `solves-different-problem` (tightening the prompt when the schema is the lever), `over-engineered` (a validation service when a nullable field would do).

## In production, beyond the guide

The API now also offers **native structured outputs** — `output_config: {format: {type: "json_schema", schema: {...}}}` constrains the *response* to a schema, and `strict: true` on a tool definition guarantees the tool input validates exactly. SDK helpers (`client.messages.parse()` with Pydantic or Zod) validate automatically.

**On the exam, tool use + JSON schema is the answer.** In production, native structured outputs are often better when you want a constrained response rather than a constrained tool call. The guarantee boundary is identical either way. See the [drift log](../exam/drift-log.md#structured-output--changed-).
