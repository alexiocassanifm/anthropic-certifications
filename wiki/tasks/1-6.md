# 1.6 — Design task decomposition strategies for complex workflows

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [1 — Agentic Architecture & Orchestration](../domains/1-agentic-architecture-and-orchestration.md) (27%)

## What it tests

Choosing between a **fixed sequential pipeline** and a **plan that adapts to what it finds**. The choice is determined by whether you know the shape of the work in advance.

## Knowledge

**Prompt chaining (fixed sequential decomposition)** fits predictable, multi-aspect work where the steps are known before you start. The guide's example: break a code review into per-file analysis passes, then a cross-file integration pass.

**Dynamic adaptive decomposition** fits open-ended investigation, where each step's findings determine the next subtasks. You cannot enumerate the steps upfront because you do not yet know what is there.

**Attention dilutes across a large pass.** Analysing many files together produces inconsistent depth — detailed on some, superficial on others, sometimes contradictory. Splitting into focused passes addresses this at the cause. This is the same fact [4.6](4-6.md) tests from the review-architecture side.

## Skills

- **Select the pattern by workflow type**: prompt chaining for predictable multi-aspect reviews; dynamic decomposition for open-ended investigation.
- **Split large code reviews** into per-file local analysis passes *plus* a separate cross-file integration pass — the integration pass is not optional, it is where cross-file data flow issues live.
- **Decompose open-ended tasks** (e.g. "add comprehensive tests to a legacy codebase") by first mapping structure, then identifying high-impact areas, then creating a prioritised plan that adapts as dependencies surface.

## Anti-patterns

- **A fixed pipeline for an unknown problem space.** You will faithfully execute a plan built on assumptions you could not have checked.
- **Adaptive decomposition for a task with known structure.** Overhead with no benefit; the plan is already knowable.
- **One big pass over everything.** The default that attention dilution punishes.
- **Per-file passes with no integration pass.** You catch local issues and miss every cross-file one — which are usually the expensive ones.
- **Decomposition that is too narrow.** [1.2](1-2.md)'s failure: a well-executed plan covering the wrong third of the problem.

## Exam angle

Recognise the two triggers:

| Stem says | Pattern |
|---|---|
| "review each file for X, Y, and Z" — aspects known upfront | Prompt chaining |
| "explore this legacy system and figure out what needs tests" | Dynamic, adaptive |
| "14 files, inconsistent depth, contradictory findings" | Split into focused passes + integration pass |

Distractor families: `shifts-burden` ("require developers to submit smaller PRs"), `over-engineered` (a larger context window — which misunderstands the cause: attention quality, not capacity), `suppresses-signal` (consensus across three runs).

The "larger context window" distractor is worth internalising. **Attention dilution is not a capacity problem.** More room to put the files does not make the model attend to each one as carefully.
