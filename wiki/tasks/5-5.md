# 5.5 — Design human review workflows and confidence calibration

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [5 — Context Management & Reliability](../domains/5-context-management-and-reliability.md) (15%)

## What it tests

How to know whether an extraction pipeline is actually good enough to trust — and how to spend limited reviewer time.

## Knowledge

**Aggregate accuracy masks segment failure.** A 97% overall figure can conceal a document type or a field performing terribly. This is the objective's central warning.

**Stratified random sampling of high-confidence extractions** measures ongoing error rates and detects novel error patterns — the ones nobody wrote a rule for.

**Field-level confidence scores calibrated using labelled validation sets** route review attention. **Calibration against labelled data is what makes confidence legitimate here**, in contrast to the self-reported confidence [5.2](5-2.md) rejects.

**Validate accuracy by document type and field segment *before* automating high-confidence extractions.**

## Skills

- Implement stratified random sampling of high-confidence extractions for ongoing error-rate measurement and novel pattern detection.
- **Analyse accuracy by document type and field** to verify consistent performance across all segments before reducing human review.
- Have models output field-level confidence scores, then calibrate review thresholds using labelled validation sets.
- Route extractions with low model confidence, or ambiguous/contradictory source documents, to human review — prioritising limited reviewer capacity.

## Anti-patterns

- **Trusting an aggregate accuracy number.** The named failure.
- **Reducing human review before segment validation.** You automate the segment that is broken.
- **Uncalibrated confidence thresholds.** A number that means nothing routes nothing correctly.
- **Reviewing only low-confidence extractions.** Then novel error patterns in the high-confidence pool are never found — which is what the stratified sample is for.

## Exam angle

The stem usually offers a tempting metric: *"The pipeline reports 97% accuracy. The team wants to reduce human review."* The answer is always **segment before you trust** — verify by document type and by field.

The stratified sampling item is the subtler one: why sample extractions you are already confident about? Because that is the only way to discover error patterns you did not know to look for. An option proposing to review only low-confidence items is the trap.

**Reconciling this with [5.2](5-2.md):** confidence is rejected there and endorsed here. The difference is calibration and scope — field-level confidence validated against labelled data, used to route review, is legitimate; a model's self-assessment of whether a whole case is too hard is not. If an item gives you a confidence score with no labelled validation set behind it, treat it as the unreliable proxy.

Distractor families: `unreliable-proxy` (uncalibrated confidence), `solves-different-problem` (improving extraction when the issue is measurement).
