# 3.2 — Create and configure custom slash commands and skills

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [3 — Claude Code Configuration & Workflows](../domains/3-claude-code-configuration-and-workflows.md) (20%)

## What it tests

Scoping (who gets it), configuration (how it runs), and the choice between a skill and CLAUDE.md.

## Knowledge

**Command scoping:**

| Location | Scope |
|---|---|
| `.claude/commands/` | Project — shared via version control |
| `~/.claude/commands/` | User — personal |

**Skills live in `.claude/skills/` as `SKILL.md` files** with frontmatter configuration.

**The three frontmatter options the guide names:**

| Field | Purpose |
|---|---|
| `context: fork` | Run the skill in an isolated sub-agent context, so its output does not pollute the main conversation |
| `allowed-tools` | Restrict tool access during skill execution |
| `argument-hint` | Prompt the developer for required parameters when they invoke the skill without arguments |

**Personal skill customisation:** create variants in `~/.claude/skills/` with different names, so you do not affect teammates.

**Skills versus CLAUDE.md** — the decision is about *when the content is needed*:

- **Skill** — on-demand invocation for a task-specific workflow
- **CLAUDE.md** — always loaded, universal standards

## Skills

- Create project-scoped slash commands in `.claude/commands/` for team-wide availability via version control.
- Use `context: fork` to isolate skills producing verbose output (codebase analysis) or exploratory context (brainstorming alternatives) from the main session.
- Configure `allowed-tools` to restrict tool access during skill execution — e.g. limiting file write operations to prevent destructive actions.
- Use `argument-hint` to prompt for required parameters.
- Choose between skills and CLAUDE.md based on whether the content is task-specific or universal.

## Anti-patterns

- **A shared command in `~/.claude/commands/`.** Nobody else gets it. Same failure as [3.1](3-1.md).
- **A verbose analysis skill without `context: fork`.** Its output floods the main conversation.
- **Putting a multi-step procedure in CLAUDE.md.** It loads every session whether or not you need it.
- **Editing a shared skill for a personal preference.** Create a variant in `~/.claude/skills/` under a different name instead.

## Exam angle

The most likely item is pure scoping: *"You want a custom `/review` command available to every developer when they clone the repository. Where does the file go?"* → `.claude/commands/` in the project repository.

Watch the distractors on that one: `~/.claude/commands/` (personal, not shared), `CLAUDE.md` (project context, not command definitions), and a `.claude/config.json` with a commands array (a configuration mechanism that does not exist).

The frontmatter items test whether you know which field does what. And expect at least one skills-versus-CLAUDE.md judgment call.

## In production, beyond the guide

Two things to know, neither of which changes the exam answer:

- **`allowed-tools` semantics are inverted in current docs** ⚠️. The guide describes it as *restricting* tool access to prevent destructive actions. Current documentation defines it as *tools Claude can use **without asking permission*** — a pre-approval, cleared at your next message. **Answer the guide's framing.** For real enforcement, use `permissions.deny` or a `PreToolUse` hook.
- **Custom commands have merged into skills.** `.claude/commands/deploy.md` and `.claude/skills/deploy/SKILL.md` both produce `/deploy`. Existing `.claude/commands/` files keep working, and the scoping facts above are unchanged.

Additional frontmatter fields that exist but the guide does not cover: `name`, `disable-model-invocation`, `user-invocable`, `model`, `agent`. See the [drift log](../exam/drift-log.md#skillmd-frontmatter--confirmed-fields-inverted-semantics-).
