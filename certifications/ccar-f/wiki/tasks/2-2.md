# 2.2 — Implement structured error responses for MCP tools

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [2 — Tool Design & MCP Integration](../domains/2-tool-design-and-mcp-integration.md) (18%)

## What it tests

Whether your error responses give the agent enough information to make a *decision*. An error is not a log line; it is an input to the next action.

## Knowledge

**The MCP `isError` flag** communicates tool failure back to the agent.

**Four error categories**, and they demand different responses:

| Category | Example | Agent should |
|---|---|---|
| **Transient** | Timeout, service unavailable | Retry |
| **Validation** | Invalid input | Fix the input and retry |
| **Business** | Policy violation | Explain to the user — do *not* retry |
| **Permission** | Insufficient access | Escalate or explain — do *not* retry |

**Uniform errors prevent recovery.** A generic `"Operation failed"` gives the agent nothing to reason with, so it does the same thing for every failure — usually retry, sometimes forever.

**Retryable versus non-retryable, expressed as structured metadata,** prevents wasted retry attempts. `isRetryable: false` on a business rule violation is what stops the loop.

## Skills

- Return structured error metadata: `errorCategory` (transient / validation / permission), an `isRetryable` boolean, and a human-readable description.
- Include `retryable: false` **plus a customer-friendly explanation** for business rule violations, so the agent can communicate appropriately rather than retry.
- **Implement local error recovery within subagents** for transient failures, propagating to the coordinator only what cannot be resolved locally — along with partial results and what was attempted.
- **Distinguish access failures from valid empty results** — a timed-out search and a successful search with zero matches are opposite situations.

## Anti-patterns

- **Generic `"Operation failed"`.** The named anti-pattern. Every failure looks alike, so every response is alike.
- **Retrying a permission error.** The predictable consequence of the above.
- **Returning an empty result set marked successful** after a timeout. This silently converts a failure into "there is nothing there", and the coordinator has no way to know. Also a [5.3](5-3.md) anti-pattern.
- **Propagating every transient blip to the coordinator** instead of recovering locally first.

## Exam angle

Two shapes:

1. *"The agent retries the same failure forever"* → error categories and `isRetryable`.
2. *"A subagent timed out but reported success with no results"* → access failure ≠ empty result.

Distractor families: `suppresses-signal` (returning empty-as-success), `over-engineered` (a retry policy engine when structured metadata would do).

**The access-failure/empty-result distinction spans two domains** — it appears here and in [5.3](5-3.md). That doubles its exam probability. Learn it once, answer it twice.
