# 4.6 — Design multi-instance and multi-pass review architectures

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [4 — Prompt Engineering & Structured Output](../domains/4-prompt-engineering-and-structured-output.md) (20%)

## What it tests

Two structural facts about review quality — one about *who* reviews, one about *how much at once*.

## Knowledge

**Self-review is structurally limited.** A model retains its reasoning context from generation, which makes it less likely to question its own decisions in the same session. This is not a prompting problem; you cannot instruct your way out of it.

**Independent review instances — without the generator's prior reasoning context — catch subtle issues** more effectively than self-review instructions or extended thinking.

**Multi-pass review:** split large reviews into per-file local analysis passes plus cross-file integration passes, to avoid attention dilution and contradictory findings.

## Skills

- Use a second independent Claude instance to review generated code, without the generator's reasoning context.
- Split large multi-file reviews into focused per-file passes for local issues, plus separate integration passes for cross-file data flow analysis.
- Run verification passes where the model self-reports confidence alongside each finding, to enable calibrated review routing.

## Anti-patterns

The guide's sample question makes all three explicit, and each is instructive:

| Wrong answer | Why |
|---|---|
| **Require developers to split large PRs into 3–4 files** | Shifts the burden to humans without improving the system |
| **Switch to a model with a larger context window** | Misunderstands the cause — attention *quality*, not capacity |
| **Run three independent passes; flag only issues appearing in at least two** | **Suppresses** detection of real bugs that are only caught intermittently |

That third one is the most instructive on the whole exam. Consensus voting feels like rigour and is actively harmful: the bugs you most need are exactly the ones a single pass catches inconsistently.

Also wrong: **instructing the generating session to review its own work carefully.** No amount of instruction removes the retained reasoning context.

## Exam angle

The canonical stem: *"A PR modifies 14 files. Your single-pass review produces inconsistent results: detailed feedback for some files, superficial comments for others, obvious bugs missed, and contradictory feedback — flagging a pattern as problematic in one file while approving identical code elsewhere in the same PR."*

Answer: split into per-file passes for local issues plus a separate integration-focused pass for cross-file data flow.

**"Contradictory feedback within one PR" is the signature symptom of attention dilution.** When you see it, the answer is decomposition, and it is the same fact as [1.6](1-6.md) from a different angle.

Note the tension with [5.5](5-5.md): self-reported confidence is listed here as a *legitimate* skill for review routing, and there as an *unreliable proxy* for case complexity. Both are the guide's positions. The reconciliation: confidence attached to a specific finding, used to route review attention, is useful; confidence used as a proxy for whether a whole case is too hard is not — and calibration against a labelled set is what separates them.

Distractor families: `shifts-burden`, `over-engineered`, `suppresses-signal`.
