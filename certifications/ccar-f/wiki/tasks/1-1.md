# 1.1 — Design and implement agentic loops for autonomous task execution

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [1 — Agentic Architecture & Orchestration](../domains/1-agentic-architecture-and-orchestration.md) (27%)

## What it tests

Whether you know what actually drives an agentic loop. The loop is simple — send a request, look at why the model stopped, run any tools it asked for, send the results back — and almost every wrong answer on this objective comes from inferring "why it stopped" instead of reading it.

## Knowledge

**The lifecycle.** One iteration is: send the request → inspect `stop_reason` → if the model asked for tools, execute them → append the results to the conversation → send again. Repeat until the model stops asking.

**`stop_reason` is the control signal.** `"tool_use"` means the model wants a tool executed and expects you to come back. `"end_turn"` means it is finished. These are not hints you interpret; they are the loop's condition.

**Tool results go back into conversation history.** They are appended as a message so the next request carries them, and the model reasons over the new information. If you drop them, or summarise them away, the model is answering from a world that no longer exists. This is where [5.1](5-1.md) starts.

**Model-driven versus pre-configured.** In an agentic loop, *Claude* decides which tool to call next from the current context. That is different from a decision tree or a fixed tool sequence you wrote in advance. The distinction matters because it is the reason the loop is worth building: the model adapts to what the tools returned. A hard-coded sequence does not.

## Skills

- Implement control flow that continues while `stop_reason` is `"tool_use"` and terminates on `"end_turn"`.
- Append tool results to conversation context between iterations, so each request carries everything learned so far.
- Handle multiple tool calls in one response — the model may request several, and all of their results go back together.

## Anti-patterns

The guide names three explicitly. Each one is a plausible-looking distractor:

| Anti-pattern | Why it fails |
|---|---|
| **Parsing natural language for a completion signal** — looking for "I'm done", "Task complete" in the assistant's prose | Brittle and probabilistic. The signal you need is already in the response, typed and reliable. |
| **An iteration cap as the *primary* stopping mechanism** | A cap is a safety net against runaway loops. As the actual termination logic it truncates work arbitrarily mid-task. |
| **Checking whether text content appeared** as a completion indicator | The model can emit text *and* request a tool in the same response. Text is not termination. |

The unifying error: **inferring termination instead of reading it.** See [deterministic vs probabilistic](../heuristics/deterministic-vs-probabilistic.md).

## Exam angle

Expect a symptom — a loop that never ends, ends early, or misses work — and four proposed fixes. The correct one reads `stop_reason`; the distractors infer.

Distractor families in play: `unreliable-proxy` (text parsing, iteration caps as control flow), `over-engineered` (a classifier deciding whether the agent is done).

Watch for items that make an iteration cap sound responsible. Caps are fine *as a backstop*; the trap is proposing one as the mechanism.

## In production, beyond the guide

`stop_reason` has more values than the two the guide names — `max_tokens`, `stop_sequence`, `pause_turn`, `refusal`. A loop that only branches on `tool_use` and `end_turn` will mishandle a paused server-side tool turn or a safety refusal. **Answer the guide's two on the exam**; handle all of them in real code. See the [drift log](../exam/drift-log.md#domain-4--prompt-engineering--structured-output).
