# 2.1 — Design effective tool interfaces with clear descriptions and boundaries

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [2 — Tool Design & MCP Integration](../domains/2-tool-design-and-mcp-integration.md) (18%)

## What it tests

That you treat the tool description as the routing mechanism it is, rather than as documentation.

## Knowledge

**Descriptions are the primary mechanism LLMs use for tool selection.** Not the name, not the schema — the description. Minimal descriptions produce unreliable selection among similar tools, structurally and predictably.

**What a good description contains:** input formats it handles, example queries, edge cases, and an explicit boundary explaining when to use *this* tool versus a similar one.

**Ambiguity causes misrouting.** The guide's example is `analyze_content` versus `analyze_document` with near-identical descriptions. If a human could not tell them apart from the descriptions, neither can the model.

**System prompt wording can override good descriptions.** Keyword-sensitive instructions in the system prompt create unintended tool associations. When descriptions are already detailed and selection is still wrong, read the system prompt.

## Skills

- Write descriptions that differentiate purpose, expected inputs, outputs, and *when to use it versus similar alternatives*.
- **Rename and re-describe to eliminate overlap** — e.g. rename `analyze_content` to `extract_web_results` with a web-specific description.
- **Split generic tools into purpose-specific ones with defined input/output contracts** — e.g. a generic `analyze_document` becomes `extract_data_points`, `summarize_content`, and `verify_claim_against_source`.
- Review system prompts for keyword-sensitive instructions that might override well-written descriptions.

## Anti-patterns

- **A routing layer that parses input and pre-selects tools.** Over-engineered, and it bypasses the language understanding you are paying for. This is the exam's favourite distractor here.
- **Few-shot examples to fix a description problem.** They help, but they add token overhead on every request without fixing the cause, and they generalise poorly to the next similar tool you add.
- **Merging overlapping tools as a *first* step.** Consolidation is a defensible architecture but it is a redesign, not a first response.
- **Leaving the description as one line** because the name seems self-explanatory.

## Exam angle

The canonical stem: *"Production logs show the agent frequently calls `get_customer` when users ask about orders. Both tools have minimal descriptions and accept similar identifier formats. What's the most effective **first step**?"*

**"First step" is the tell.** Expand both descriptions with input formats, example queries, edge cases, and explicit boundaries. It is the cheapest fix and it hits the stated cause.

Distractor families: `over-engineered` (routing layer), `solves-different-problem` (few-shot examples — real but aimed at the symptom), and a consolidation option that is architecturally fine but disproportionate as a first move.

See [cheapest fix at the root cause](../heuristics/cheapest-fix-at-root-cause.md) — this objective is that heuristic's clearest instance.
