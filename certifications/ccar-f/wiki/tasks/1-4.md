# 1.4 — Implement multi-step workflows with enforcement and handoff patterns

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [1 — Agentic Architecture & Orchestration](../domains/1-agentic-architecture-and-orchestration.md) (27%)

## What it tests

When to guarantee an ordering in code rather than asking for it in a prompt — and what a good handoff to a human looks like.

## Knowledge

**Programmatic enforcement versus prompt-based guidance.** Hooks and prerequisite gates *guarantee*. Prompt instructions *encourage*. Both are legitimate; the question is always which the situation requires.

**When compliance must be deterministic, prompt instructions have a non-zero failure rate.** The guide states this directly, using identity verification before financial operations as the example. "Non-zero" is the whole point: a 3% failure rate on refunds is a production incident, not a rounding error.

**Structured handoff protocols** for mid-process escalation carry customer details, root cause analysis, and recommended actions — because the human receiving the escalation does not have your conversation transcript.

## Skills

- **Implement programmatic prerequisites that block downstream tool calls** until a prerequisite step has completed — e.g. blocking `process_refund` until `get_customer` has returned a *verified* customer ID.
- **Decompose multi-concern requests** into distinct items, investigate each in parallel using shared context, then synthesise a unified resolution.
- **Compile structured handoff summaries** — customer ID, root cause, refund amount, recommended action — when escalating to a human who lacks the transcript.

## Anti-patterns

- **Strengthening the prompt when the requirement is a guarantee.** "Enhance the system prompt to state that verification is *mandatory*" is the archetypal wrong answer. It moves 12% to maybe 3%; it does not solve the problem.
- **Few-shot examples for an ordering invariant.** Same failure, more tokens.
- **Fixing tool *availability* when the problem is tool *ordering*.** A routing classifier that enables a subset of tools per request type addresses which tools exist, not which runs first.
- **Escalating with no context.** A handoff that says "customer needs help with a refund" wastes the human's first five minutes.

## Exam angle

The canonical stem: *"Production data shows that in N% of cases, your agent skips [verification step] and calls [action] using only [weak identifier], occasionally leading to [financial consequence]."*

The answer is a programmatic prerequisite. Everything else on the list will be a prompt-level or availability-level fix.

**The tell is money or identity.** When the stem mentions refunds, payments, account access, or a policy that must never be violated, [deterministic vs probabilistic](../heuristics/deterministic-vs-probabilistic.md) overrides [cheapest fix at the root cause](../heuristics/cheapest-fix-at-root-cause.md), and the more expensive hook wins.

Distractor families: `prompt-instead-of-enforcement` (the dominant one), `solves-different-problem` (tool availability vs tool ordering), `over-engineered` (a classifier).
