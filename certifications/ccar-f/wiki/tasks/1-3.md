# 1.3 — Configure subagent invocation, context passing, and spawning

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [1 — Agentic Architecture & Orchestration](../domains/1-agentic-architecture-and-orchestration.md) (27%)

## What it tests

The mechanics of spawning subagents and — the load-bearing half — getting information across the boundary between them.

## Knowledge

**`Task` is the spawning mechanism, and it must be in `allowedTools`.** A coordinator that cannot spawn is usually a coordinator whose `allowedTools` omits `"Task"`. This is a concrete, checkable fact and an easy exam item.

**Subagent context must be explicitly provided in the prompt.** Subagents do not automatically inherit parent context, and they do not share memory between invocations. If the synthesis agent needs the search results, you put the search results in its prompt. There is no ambient state.

**`AgentDefinition`** configures each subagent type: its description, its system prompt, and its tool restrictions. Tool restrictions here are where [2.3](2-3.md) and [least-privilege tooling](../heuristics/least-privilege-tooling.md) meet this objective.

**Fork-based session management** lets you explore divergent approaches from a shared analysis baseline — branch once the expensive context-building is done. See [1.7](1-7.md).

## Skills

- **Include complete findings from prior agents directly in the subagent's prompt** — pass the web search results and document analysis outputs into the synthesis subagent, not a pointer to them.
- **Use structured formats that separate content from metadata** — source URLs, document names, page numbers travel *alongside* the content, not embedded in prose. This is what makes attribution survive the handoff, and it is the mechanism [5.6](5-6.md) depends on.
- **Spawn in parallel by emitting multiple `Task` calls in a single coordinator response** — not across separate turns. Sequential spawning is the latency bug this skill exists to prevent.
- **Write coordinator prompts that specify goals and quality criteria, not step-by-step procedure** — prescriptive scripts prevent the subagent from adapting to what it actually finds.

## Anti-patterns

- **Assuming inheritance.** "The subagent will have the conversation history" is wrong, and it is the root cause behind a large share of multi-agent items.
- **Sequential spawning across turns** when the work is independent — one `Task` call per turn serialises what should be parallel.
- **Step-by-step procedural coordinator prompts** — they cap the subagent at whatever you anticipated.
- **Passing prose summaries between agents** — metadata dissolves, and [5.6](5-6.md)'s provenance problem begins.

## Exam angle

Two recurring shapes:

1. *"The synthesis agent has no idea what the search agent found."* → context was not passed explicitly.
2. *"Subagents run one after another and latency is 4× what it should be."* → emit multiple `Task` calls in a single response.

Distractor families: `solves-different-problem` (fixing the synthesis prompt when the input was never delivered), `over-engineered` (building a shared state store when the prompt should carry the findings).

Note the interaction with [1.2](1-2.md): if an item describes a *coverage* failure, look at decomposition. If it describes a *knowledge* failure — an agent not knowing something an earlier agent found — look at context passing.
