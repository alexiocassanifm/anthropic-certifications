# 4.1 — Design prompts with explicit criteria to improve precision and reduce false positives

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [4 — Prompt Engineering & Structured Output](../domains/4-prompt-engineering-and-structured-output.md) (20%)

## What it tests

That you replace exhortation with specification. This objective is one long argument against telling the model to try harder.

## Knowledge

**Explicit criteria beat vague instructions.** The guide's contrast: *"flag comments only when claimed behavior contradicts actual code behavior"* versus *"check that comments are accurate."* The first is checkable; the second is a wish.

**General instructions do not improve precision.** *"Be conservative"* and *"only report high-confidence findings"* are named as failures. They do not give the model anything to apply. Specific categorical criteria do.

**False positive rates destroy trust asymmetrically.** A single high-false-positive category undermines confidence in the accurate categories too. Trust is not averaged across the system; one noisy category poisons the whole output.

## Skills

- Write specific review criteria defining which issues to report (bugs, security) and which to skip (minor style, local patterns) — rather than relying on confidence-based filtering.
- **Temporarily disable high-false-positive categories** to restore developer trust while you improve the prompts for those categories.
- Define explicit severity criteria **with concrete code examples for each level** to achieve consistent classification.

## Anti-patterns

- **"Be conservative."** Named in the guide as ineffective.
- **"Only report high-confidence findings."** Same — and it compounds the [5.5](5-5.md) problem, since self-reported confidence is poorly calibrated.
- **A global confidence threshold** instead of per-category criteria. Trust is per-category; the fix should be too.
- **Severity levels defined by adjective** — "high", "medium", "low" with no examples. Classification drifts run to run.

## Exam angle

The signature move is **temporarily disabling a category**. It feels like giving up, which is why it is testable: the reasoning is that developer trust is the scarce resource, and a category producing 40% noise is actively destroying the value of the four categories that work. Turn it off, fix its criteria, turn it back on.

Expect items offering a global threshold or a confidence filter as the tempting alternative. Both are the vague-instruction anti-pattern wearing a number.

Distractor families: `unreliable-proxy` (confidence thresholds), `solves-different-problem` (tuning the model or the review scope rather than the criteria).
