# 1.7 — Manage session state, resumption, and forking

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [1 — Agentic Architecture & Orchestration](../domains/1-agentic-architecture-and-orchestration.md) (27%)

## What it tests

Returning to earlier work — and the judgment call about whether returning is even the right move.

## Knowledge

**Named session resumption** with `--resume <session-name>` continues a specific prior conversation.

**`fork_session`** creates an independent branch from a shared analysis baseline. The point is to do the expensive context-building once and then explore divergent approaches from it — two testing strategies, two refactoring approaches — without redoing the analysis or contaminating either branch.

**Resuming after code changes is dangerous.** The session's tool results describe files as they were. If the files changed, the agent is confidently reasoning about a codebase that no longer exists. You must tell it what changed.

**Sometimes a fresh session beats resumption.** The guide states this explicitly: starting new with a structured summary is *more reliable* than resuming with stale tool results. This is counterintuitive — resumption feels like the thorough choice — and that is exactly why it is testable.

## Skills

- Use `--resume` with session names to continue named investigation sessions across working sessions.
- Use `fork_session` to create parallel exploration branches from a shared codebase analysis.
- **Choose between resumption and a fresh start**: resume when prior context is mostly still valid; start fresh with an injected summary when prior tool results have gone stale.
- Inform a resumed session about *specific* file changes so it can re-analyse those targets, rather than forcing a full re-exploration.

## Anti-patterns

- **Resuming a session after significant code changes without saying what changed.** The agent's picture is wrong and it does not know.
- **Full re-exploration when a targeted note would do.** If three files changed, say which three.
- **Forking when you needed a fresh start.** A fork inherits the stale baseline too.

## Exam angle

Expect a judgment item: *"You resumed a session after modifying the files it had analysed. What now?"* The gradient runs:

1. Tell it exactly what changed → targeted re-analysis. **Best when most context is still valid.**
2. Start fresh with a structured summary. **Best when the tool results are broadly stale.**
3. Resume and hope. **Never.**
4. Full re-exploration from scratch with no summary. **Wasteful.**

Distractor families: `solves-different-problem`, `shifts-burden`.

The `fork_session` items are usually cleaner: "compare two approaches from the same analysis" → fork.

## In production, beyond the guide

The CLI `--resume` accepts an ID *or* a name; the Agent SDK's `resume` option takes an **ID**, with `rename_session()` / `tag_session()` as separate functions. There is also `--continue` / `continue_conversation`, which resumes the most recent session with no ID at all — not mentioned in the guide. Sessions live at `~/.claude/projects/<encoded-cwd>/*.jsonl`. See the [drift log](../exam/drift-log.md#session-resumption--changed-nuance).
