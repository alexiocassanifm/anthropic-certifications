# 4.2 — Apply few-shot prompting to improve output consistency and quality

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [4 — Prompt Engineering & Structured Output](../domains/4-prompt-engineering-and-structured-output.md) (20%)

## What it tests

When examples are the right instrument — and, quietly, that **volume is not the mechanism**.

## Knowledge

**Few-shot examples are the most effective technique for consistently formatted, actionable output when detailed instructions alone produce inconsistent results.** The trigger is *"we already wrote detailed instructions and it still varies."*

**Examples carry judgment on ambiguous cases** — tool selection for ambiguous requests, branch-level test coverage gaps — in a way instructions cannot.

**Examples enable generalisation to novel patterns**, rather than matching only the cases you enumerated. This is the argument against writing a longer rule list.

**Examples reduce hallucination in extraction tasks** — informal measurements, varied document structures.

## Skills

- Create **2–4 targeted examples for ambiguous scenarios**, each showing the *reasoning* for why one action was chosen over a plausible alternative.
- Include examples demonstrating the desired output format — location, issue, severity, suggested fix.
- Provide examples distinguishing acceptable code patterns from genuine issues, reducing false positives while still enabling generalisation.
- Demonstrate correct handling of varied document structures — inline citations versus bibliographies, methodology sections versus embedded details.
- Add examples showing correct extraction from documents with varied formats, to fix empty or null extraction of required fields.

## Anti-patterns

- **More examples as the fix.** Note the count the guide uses: **2–4 targeted** examples. When a distractor proposes "5–8 examples showing…", the number itself is a signal — volume is not the mechanism, and in [2.1](2-1.md)'s sample question the many-examples option loses to a better tool description.
- **Examples without reasoning.** Showing the choice without showing *why* teaches pattern-matching, not judgment.
- **Examples for a description problem.** If tool selection is failing because two descriptions are indistinguishable, fix the descriptions ([2.1](2-1.md)).
- **Enumerating every case in rules** instead of demonstrating the judgment.

## Exam angle

The distinguishing question is always: *is the problem inconsistency, or is it something else wearing inconsistency's clothes?*

| Symptom | Answer |
|---|---|
| Detailed instructions, still inconsistent output format | Few-shot examples |
| Ambiguous cases handled inconsistently | 2–4 examples showing the reasoning |
| Extraction returns empty on varied document formats | Examples covering the format variety |
| Two tools with thin descriptions get confused | **Not** few-shot — fix the descriptions ([2.1](2-1.md)) |
| An ordering invariant is sometimes violated | **Not** few-shot — a prerequisite gate ([1.4](1-4.md)) |

Those last two rows are where the exam earns its money. Few-shot is a strong, correct technique that is *also* the most common wrong answer in this exam, because it plausibly helps almost everything. Ask whether it addresses the stated cause.

Distractor families: `solves-different-problem`, `prompt-instead-of-enforcement`.
