# 5.2 — Design effective escalation and ambiguity resolution patterns

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [5 — Context Management & Reliability](../domains/5-context-management-and-reliability.md) (15%)

## What it tests

When an agent should stop and hand over — and it is full of fine distinctions that the exam tests directly.

## Knowledge

**The three legitimate escalation triggers:**

1. The customer **requests a human**
2. A **policy exception or gap** — note: *not merely a complex case*
3. **Inability to make meaningful progress**

**Explicit request versus offering to resolve.** If the customer explicitly demands a human, escalate immediately. If the issue is straightforward and they are simply frustrated, offer to resolve it.

**Sentiment and self-reported confidence are unreliable proxies for case complexity.** Both are named. Sentiment measures annoyance, not difficulty. Self-reported confidence is poorly calibrated — the agent is already confidently wrong on the hard cases.

**Multiple matches require clarification, not heuristic selection.** Ask for another identifier.

## Skills

- Add explicit escalation criteria **with few-shot examples** to the system prompt, demonstrating when to escalate versus resolve autonomously.
- **Honour explicit customer requests for human agents immediately, without first attempting investigation.**
- **Acknowledge frustration while offering resolution** when the issue is within the agent's capability — escalating only if the customer reiterates their preference.
- **Escalate when policy is ambiguous or silent** on the customer's specific request — e.g. competitor price matching when policy only addresses own-site adjustments.
- Instruct the agent to ask for additional identifiers when tool results return multiple matches, rather than selecting on heuristics.

## Anti-patterns

- **Sentiment-based escalation.** Solves a different problem entirely; sentiment does not correlate with complexity.
- **Self-reported confidence thresholds.** The agent is incorrectly confident on hard cases, so this routes exactly the wrong ones.
- **A separately trained classifier** to predict which requests need escalation. Over-engineered: requires labelled data and ML infrastructure when prompt optimisation has not been tried.
- **Investigating first when the customer asked for a human.** Well-intentioned and wrong.
- **Escalating every complex case.** Complexity is not a trigger; a policy gap is.
- **Picking a customer heuristically** when several match.

## Exam angle

The canonical stem: *"Your agent achieves 55% first-contact resolution against an 80% target. Logs show it escalates straightforward cases (standard damage replacements with photo evidence) while attempting to autonomously handle complex situations requiring policy exceptions. What's the most effective way to improve escalation calibration?"*

Answer: explicit escalation criteria with few-shot examples. The root cause is unclear decision boundaries, and this is the proportionate first response before adding infrastructure.

Know why each distractor fails:

| Distractor | Failure |
|---|---|
| Self-reported confidence (1–10) with a threshold | LLM self-reported confidence is poorly calibrated — the agent is already incorrectly confident on hard cases |
| A classifier trained on historical tickets | Over-engineered; needs labelled data and ML infrastructure before prompt optimisation was tried |
| Sentiment analysis on frustration levels | Solves a different problem — sentiment does not correlate with case complexity |

Distractor families: `unreliable-proxy` (the dominant one), `over-engineered`.
