# 3.6 — Integrate Claude Code into CI/CD pipelines

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [3 — Claude Code Configuration & Workflows](../domains/3-claude-code-configuration-and-workflows.md) (20%)

## What it tests

Running Claude Code where no human is present: non-interactive execution, machine-parseable output, and supplying the context an interactive user would have provided by conversation.

## Knowledge

**`-p` (or `--print`)** runs Claude Code in non-interactive mode. Without it, a CI job waits for input and hangs indefinitely.

**`--output-format json` with `--json-schema`** enforces structured output, producing machine-parseable findings you can post as inline PR comments.

**CLAUDE.md is how you give a CI-invoked Claude project context** — testing standards, fixture conventions, review criteria. An interactive user supplies this by talking; a pipeline cannot.

**Session context isolation:** the same session that generated code is less effective at reviewing its own changes than an independent review instance, because it retains its reasoning context from generation.

## Skills

- Run Claude Code in CI with `-p` to prevent interactive input hangs.
- Use `--output-format json` with `--json-schema` to produce machine-parseable structured findings for automated inline PR comments.
- **Include prior review findings in context** when re-running after new commits, instructing Claude to report only new or still-unaddressed issues — this is what stops duplicate comments.
- **Provide existing test files in context** so test generation avoids duplicating scenarios already covered.
- Document testing standards, valuable test criteria, and available fixtures in CLAUDE.md to improve test generation quality and reduce low-value output.

## Anti-patterns

- **Running without `-p`.** The job hangs. The guide's own sample question covers this, and the distractors are all plausible-sounding non-existent mechanisms — a `CLAUDE_HEADLESS` environment variable, a `--batch` flag, redirecting stdin from `/dev/null`.
- **Parsing prose output with regex** instead of requesting JSON against a schema.
- **Re-running a review with no prior-findings context.** The same twelve comments appear on every push and developers stop reading.
- **Generating tests without showing the existing suite.** You get duplicates.
- **Letting the generating session review its own work.**

## Exam angle

The `-p` item is close to free — take it. Watch for invented flags among the distractors; the exam uses non-existent features as distractors here more than anywhere else.

The higher-value items are the *context* ones. Notice the shared shape: **duplicate comments, duplicate tests, and low-value tests are all the same failure** — the pipeline did not supply context an interactive user would have given. That single insight covers three of the five skills.

Distractor families: `solves-different-problem` (Unix workarounds for what is a flag), `shifts-burden`.

## In production, beyond the guide

All flags verified exactly. `--output-format` accepts `text`, `json`, and `stream-json`; the guide names `json`. `--json-schema` is print-mode only. Also worth knowing for CI: **`claude -p` runs load project-scoped `.mcp.json` servers without the interactive approval prompt** — see the [drift log](../exam/drift-log.md#project-server-approval-in-headless-mode--extended).
