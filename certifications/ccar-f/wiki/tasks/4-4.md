# 4.4 — Implement validation, retry, and feedback loops for extraction quality

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [4 — Prompt Engineering & Structured Output](../domains/4-prompt-engineering-and-structured-output.md) (20%)

## What it tests

What to do about the errors [4.3](4-3.md)'s schema cannot catch — and knowing when retrying is pointless.

## Knowledge

**Retry-with-error-feedback:** append the *specific* validation error to the prompt on retry, so the model can correct rather than guess. A bare "try again" retries the same reasoning.

**The limit of retry** — the highest-value fact here: **retries are ineffective when the required information is simply absent from the source document.** They work for format and structural errors. They cannot conjure data that is not there.

**Feedback loop design:** track which code constructs trigger findings via a `detected_pattern` field, enabling systematic analysis of dismissal patterns.

**Two error classes:** semantic validation errors (values do not sum, wrong field placement) versus schema syntax errors (eliminated by tool use).

## Skills

- Implement follow-up requests including the original document, the failed extraction, and the specific validation errors, for model self-correction.
- **Identify when retries will be ineffective** (the information exists only in an external document not provided) versus when they will succeed (format mismatches, structural output errors).
- Add `detected_pattern` fields to structured findings to enable analysis of false positive patterns when developers dismiss findings.
- **Design self-correction validation flows**: extract `calculated_total` alongside `stated_total` to flag discrepancies; add `conflict_detected` booleans for inconsistent source data.

## Anti-patterns

- **Retrying when the data is absent.** Burns tokens forever. Distinguish "the model got it wrong" from "the document does not contain this".
- **Blind retry** with no error detail. Same input, same reasoning, same failure.
- **Trusting a single extracted total.** Extract both the stated and the calculated value and compare — that is how you catch what the schema cannot.
- **Silently reconciling inconsistent source data.** Flag it with `conflict_detected` and let a human or downstream rule decide.

## Exam angle

The discriminating item: *"The validation-retry loop keeps failing on the same documents."* → is the information present in the source? If not, retry is the wrong instrument entirely; the answer is to detect the condition and route it, not to retry harder.

The `calculated_total` / `stated_total` pattern is distinctive enough to be memorable, and it is the guide's named technique for semantic self-correction. Expect it as a correct answer where the distractors propose stricter schemas (which cannot help — see [4.3](4-3.md)) or more retries.

Distractor families: `solves-different-problem` (tightening the schema against a semantic error), `over-engineered` (a separate validation model).
