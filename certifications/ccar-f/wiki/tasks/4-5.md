# 4.5 — Design efficient batch processing strategies

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [4 — Prompt Engineering & Structured Output](../domains/4-prompt-engineering-and-structured-output.md) (20%)

## What it tests

Matching an API to a latency requirement. The facts are few and fixed, which makes these items very scorable.

## Knowledge

**The Message Batches API:**

| Property | Value |
|---|---|
| Cost | **50% saving** |
| Processing window | **Up to 24 hours** |
| Latency SLA | **None guaranteed** |
| Multi-turn tool calling within a request | **Not supported** |
| Correlation | `custom_id` on request/response pairs |

**Appropriate for** non-blocking, latency-tolerant workloads: overnight reports, weekly audits, nightly test generation.

**Inappropriate for** blocking workflows: pre-merge checks where a developer is waiting.

**No multi-turn tool calling** means a batch request cannot execute tools mid-request and return results. An agentic loop cannot run inside one batch request.

## Skills

- Match the API to the workflow's latency requirements: synchronous for blocking pre-merge checks, batch for overnight and weekly analysis.
- **Calculate batch submission frequency from SLA constraints** — e.g. 4-hour submission windows to guarantee a 30-hour SLA with 24-hour batch processing.
- Handle batch failures by resubmitting **only the failed documents**, identified by `custom_id`, with appropriate modifications such as chunking documents that exceeded context limits.
- Use prompt refinement on a sample set before batch-processing large volumes, to maximise first-pass success and reduce iterative resubmission costs.

## Anti-patterns

- **Moving a blocking workflow to batch for the cost saving.** The named failure. No latency SLA means a developer could wait until tomorrow.
- **"Batch usually completes faster than the maximum, so it's fine."** The guide rejects reliance on typical completion time for blocking work. Design against the guarantee, not the average.
- **Resubmitting the whole batch** when a few documents failed. `custom_id` exists so you do not have to.
- **"Batch results come back out of order, so we can't use it."** A misconception — `custom_id` correlates them.
- **A timeout fallback to real-time** if the batch takes too long. Unnecessary complexity when the right answer is matching each workflow to its API.

## Exam angle

The canonical stem: *"Your manager proposes switching both a blocking pre-merge check and an overnight technical-debt report to the Batches API for its 50% cost savings. How should you evaluate this?"*

**The answer splits them.** Batch for the overnight report, keep real-time for the pre-merge check. This shape — a proposal that is half right — appears whenever the guide's "evaluate this proposal" phrasing shows up.

The SLA arithmetic item is worth practising once: if processing takes up to 24 hours and you must guarantee 30, submissions every 4 hours leaves headroom. Do the subtraction rather than eyeballing it.

Distractor families: `solves-different-problem` (a timeout fallback), plus options built on the ordering misconception.

## In production, beyond the guide

Every guide fact verified. Additional limits not in the guide: up to 100,000 requests or 256 MB per batch, most batches complete within an hour, results retained for 29 days. See the [drift log](../exam/drift-log.md#message-batches-api--confirmed-extended).
