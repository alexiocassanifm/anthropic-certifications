# 3.4 — Determine when to use plan mode vs direct execution

> Task statement title reproduced from *Exam Guide v1.0*. Everything below is this project's own explanation.

**Domain:** [3 — Claude Code Configuration & Workflows](../domains/3-claude-code-configuration-and-workflows.md) (20%)

## What it tests

A judgment call with a clear rule underneath it: plan when the *approach* is uncertain, execute directly when only the *work* remains.

## Knowledge

**Plan mode is for** complex tasks involving large-scale changes, multiple valid approaches, architectural decisions, and multi-file modifications.

**Direct execution is for** simple, well-scoped changes — adding a single validation check to one function.

**Plan mode enables safe exploration and design before committing to changes**, which prevents costly rework when dependencies surface late.

**The Explore subagent** isolates verbose discovery output and returns summaries, preserving the main conversation's context.

## Skills

- Select plan mode for tasks with architectural implications: microservice restructuring, library migrations affecting 45+ files, choosing between integration approaches with different infrastructure requirements.
- Select direct execution for well-understood changes with clear scope: a single-file bug fix with a clear stack trace, adding a date validation conditional.
- Use the Explore subagent for verbose discovery phases to prevent context window exhaustion during multi-phase tasks.
- Combine both: plan mode for investigation, direct execution for implementation.

## Anti-patterns

- **"Start with direct execution and switch to plan mode if it gets complicated."** The guide rejects this explicitly when the complexity is *already stated in the requirements*. You are not discovering complexity; you were told about it.
- **"Make changes incrementally and let the implementation reveal the structure."** Risks costly rework when dependencies are discovered late.
- **"Direct execution with comprehensive upfront instructions."** Assumes you already know the right structure without exploring the code.
- **Plan mode for a one-line fix.** Overhead with no return.

## Exam angle

The canonical stem: *"You've been assigned to restructure the team's monolithic application into microservices. This involves changes across dozens of files and requires decisions about service boundaries and module dependencies."* → plan mode.

The three distractors map exactly to the anti-patterns above, and each fails for its own stated reason. Learn the reasons, not just the answer — items vary which distractor is most tempting.

**Both signals must be present for plan mode**: scale *and* genuine uncertainty about the approach. A migration touching 45 files with one obvious mechanical transformation is large but not uncertain. An architectural choice affecting three files is small but uncertain. The guide's examples pair them.

Distractor families: `solves-different-problem`, and a subtle one — options that sound appropriately cautious ("switch if needed") while ignoring information already in the stem.
